# Predictive Logistics & Forward Supply Chain — SIH · PS 26251

> **Prototype uses fictional synthetic logistics data and is intended for decision-support demonstration only.**
>
> All depots, forward locations, routes, vehicles, terrain, weather, consumption and sensor telemetry in this repository are
> fictional and generated by a seeded script. Nothing here represents real Army data, real bases, real operational routes,
> troop/unit positions, deployments or real sensors, and the prototype is **not** production military software. Every
> recommendation is a decision-support output computed from fictional synthetic scenarios; final decisions rest with authorised personnel.

Full-stack upgrade of the v3 HTML prototype (kept untouched in `legacy/v3/`) into **React + Vite + TypeScript + Tailwind** ·
**FastAPI + Pydantic + SQLAlchemy** · **PostgreSQL + PostGIS** · **Docker Compose**, with a simulated ESP32/RFID layer.

---

## 1. Problem statement (PS 26251)

*Indian Army – Predictive Logistics & Forward Supply Chain.* Forward locations in difficult terrain are resupplied over long,
weather-exposed routes. Planners need to **predict consumption, see shortages before they happen, decide what to send first, and pick routes and
vehicles that can actually deliver** — and to understand *why* a location is at risk.

## 2. Solution overview

| Need | What the prototype does |
|---|---|
| Predict demand | Weather-aware statistical forecast per location × supply, 7/14/30-day horizons, 80 % interval, backtest MAPE, confidence; Random Forest challenger as a cross-check |
| See shortages early | Days-of-supply, 14-day predicted shortage, stock-out date, GREEN/YELLOW/RED (NORMAL/WARNING/CRITICAL) classification, explainable "Why at risk" |
| Decide what first | Supply priority queue (score 0–100) from shortage, stock deficit, criticality, lead time, route feasibility, transport capacity |
| Decide how | Route optimisation (distance, ETA, vehicle capacity, road, weather, **terrain**) with alternatives and a stated reason; allocation within real depot stock and vehicle capacity |
| Test resilience | What-If simulation: demand, weather, road, vehicle availability → before/after metrics + explanations |
| Near-real-time inventory | Simulated ESP32/RFID events → FastAPI → PostgreSQL → inventory, alerts, priority, allocation, dashboard |

## 3. Architecture

```
 Browser (React + Leaflet + Recharts)            iot-simulator/simulator.py  (simulated ESP32/RFID)
        │  /api/*                                         │  POST /api/iot/update
        ▼                                                 ▼
   nginx :8080 ───────────────────────────────►  FastAPI :8000  (routers → services → repository)
   (static SPA + /api proxy)                       │  pure engines: forecasting · inventory · terrain · routing
                                                   │  priority · allocation · simulation · recommendation · iot
                                                   ▼

```

* **Business logic lives in the backend.** The frontend only renders API responses (scenario sliders are sent as query parameters or to `POST /api/simulation/run`).
* `backend/app/services/*` are **pure functions** over plain dataclasses (no DB) so they are unit-testable; `repository.py` loads a `Snapshot` from PostgreSQL/PostGIS and persists derived data.

### Start-up and failure behaviour
* **nginx** resolves the backend per request (`resolver 127.0.0.11` + variable upstream), so the frontend container starts and serves the UI even if the backend is down, restarting or not yet created; `/api/*` returns 502 and the UI shows "Backend unavailable" with Retry. A recreated backend with a new IP is picked up without restarting nginx. `/healthz` reports nginx liveness only.
* **Compose:** `db` health uses TCP (`pg_isready -h 127.0.0.1`) so it cannot report ready during the image's first-run init; `backend` waits for a healthy `db`; `frontend` only waits for the backend to *start* (not to be healthy), so a slow backend never aborts `docker compose up`; services use `restart: unless-stopped`.
* **Backend:** if the first bootstrap fails (database unreachable/not yet seeded), it keeps retrying in the background every 5 s until it succeeds — no manual restart. `/api/health` returns 503 `degraded` meanwhile.

## 6. Database & PostGIS

`db/schema.sql` (all tables have keys/constraints; PostGIS extension enabled):

`supplies` · `locations` (PostGIS `Point,4326`, GiST index) · `depots` · `vehicles` · `routes` (PostGIS `LineString,4326`, GiST) · `terrain` (generated column `terrain_risk`) ·
`weather` · `consumption` (5,500 rows) · `inventory` (forward + depot stock, safety stock) · `forecasts` · `alerts` · `priority_scores` · `allocations` · `iot_events` · `simulation_runs`, plus view `v_consumption_enriched`.

The backend genuinely uses the database: forecasts are computed from `consumption` + `weather` and stored in `forecasts`; inventory, routes, terrain and vehicles are read from their tables;
coordinates/polylines are read via `ST_X/ST_Y/ST_AsGeoJSON`; route polyline length is measured by PostGIS (`ST_Length(geography)`, shown on the route card); baseline alerts, priority scores and allocations are persisted and refreshed on start-up and after every IoT event; simulation runs and IoT events are stored.

**Synthetic data** (seed 2026, deterministic): 3 depots, 5 forward locations, 10 supply types, 8 routes, 8 vehicles (one in maintenance), 140 weather days (110 observed + 30 outlook), **5,500** consumption records (5 × 10 × 110).
Relationships: demand = base × location factor × slow trend × weather effect (per-supply sensitivity) × weekly cycle × noise; stock levels are set relative to forecast demand; lead time derives from route ETA, which derives from distance, road, weather and terrain.
Coordinates are arbitrary points in a made-up grid (`Base_01 (fictional)` etc.).

## 8. Forecasting methodology

Statistical time-series model (**not** a trained ML model), deterministic: history is de-weathered and de-seasonalised, smoothed with an EWMA (α = 0.2), extended with a damped linear trend (0.5 × recent 7-day slope), then re-weathered with the synthetic 30-day weather outlook and re-seasonalised (weekly cycle).
Weather multiplier = `1 + sensitivity × 0.6 × weather_index`. Backtest: rolling one-step-ahead over the last 60 days → MAPE, RMSE, coefficient of variation, interval coverage (±1.28 σ). Confidence = `100 − MAPE × (1 + horizon/30)` (a stated heuristic).
**Random Forest challenger** (scikit-learn, 20 trees, depth 6, seeded) is trained on days 1–90 and validated on days 91–110; on this data it scores ≈ 4.8 % hold-out MAPE vs ≈ 3.7 % for the statistical model. It is a cross-check only and does not drive any dashboard number.
*Caveat:* the synthetic history is generated from the same weather/weekly structure the model assumes, so the low error is expected and says nothing about real-world accuracy.

## 9. Inventory & risk engine

* Days of supply = stock ÷ forecast daily demand (first 7 forecast days, scenario-adjusted).
* Predicted shortage (14 d) = max(0, demand × 14 − stock). Stock-out date = sim-clock + days of supply.
* **CRITICAL (red)**: cover < 3 d or < lead time + 1 d · **WARNING (yellow)**: cover < lead time + 3 d or stock < safety stock · else **NORMAL (green)**.
* Replenishment quantity = safety + demand × (lead + 5 d) − stock, rounded to 50-unit loads.
* Location status: ≥ 2 critical items → CRITICAL; ≥ 1 critical or ≥ 3 warning → WARNING.
* Overall risk index (0–100) = `100 × min(1, 2.2·crit/N + 0.8·warn/N + 0.3·mean route risk + 0.2·capacity-deficit share)`.
* **Why at risk**: per location, the top items with demand change vs the last 7 days, stock vs safety stock, cover vs lead time, best-route risk and weather index, as a plain-language summary.

## 10. Terrain, route optimisation & GIS

* Terrain risk = `0.7 × difficulty + 0.3 × elevation_band/3` (fictional bands 0–3, e.g. "High-altitude ridge").
* Effective speed = `nominal × (1 − 0.45·road) × (1 − 0.35·terrain risk) × (1 − 0.3·weather risk)` (floor 8 km/h); **ETA = distance ÷ effective speed**. Weather risk on a route = weather × (0.5 + 0.5·terrain risk), so terrain amplifies weather.
* Route risk = `0.25 road + 0.25 weather + 0.30 terrain + 0.20 distance factor`.
* **Route selection**: combined score = route risk + ETA/24 h + capacity penalty (≤ 0.2, grows when the depot's available vehicle capacity is below the quantity to move). A route is feasible only if its depot has an available vehicle. `GET /api/routes/compare` returns all routes, scores, SELECTED/ALTERNATIVE/NO VEHICLE and a written reason.
* **Leaflet + OpenStreetMap** map: status-coloured markers (normal / warning / critical), square depot markers, risk-coloured route lines (dashed = poor road), a toggleable terrain band layer, popups with inventory, shortage, ETA, terrain, weather and capacity. If OSM tiles cannot load, a notice appears and the overlay keeps working on a plain background.

## 11. Priority & allocation

Priority score (0–100) = `100 × (0.30 shortage urgency + 0.15 shortage volume + 0.15 stock deficit + 0.15 supply criticality + 0.10 lead-time pressure + 0.10 route feasibility/risk + 0.05 transport capacity)`. Weights are fixed, documented prototype assumptions (`GET /api/priority/weights`).
Allocation walks the queue in priority order; for each item it tries routes in combined-score order, ships at most the **depot's actual stock** of that supply (depot stock is a finite synthetic quantity, ≈ 8 days of network demand) and loads vehicles within **effective vehicle capacity** (smallest sufficient vehicle first). Unmet quantity is reported with its binding constraint (`VEHICLE CAPACITY`, `DEPOT STOCK`, `NO FEASIBLE ROUTE`).
The per-item "AI Logistics Insight" is a stand-alone, **deterministic rule-based** recommendation (no external AI model) assuming full fleet availability; the allocation plan resolves vehicle contention across all items, so the vehicle shown can differ — the UI/API say so.

## 12. IoT simulation

`iot-simulator/simulator.py` (or the UI scanner, or `POST /api/iot/simulate`) emits simulated ESP32/RFID scans: `RECEIVE` (+), `ISSUE` (−, never below 0), `COUNT` (set). Each goes through `POST /api/iot/update` → validated → stored in `iot_events` → `inventory` updated → alerts/priority/allocation refreshed → dashboard recalculated. Every response and UI panel is labelled **simulated**; the `simulated` column is constrained to `true`. No hardware is involved.

## 13. What-If simulation

Controls: demand +0–50 %, weather severity, road condition, vehicle availability 50–100 %. `POST /api/simulation/run` recomputes the baseline and the scenario and returns before/after: critical/warning items, shortage-risk locations, expected shortage, transport capacity/need/deficit, mean route risk, mean ETA delay, overall risk index, allocated/unmet units, per-location status and per-route ETA/risk, plus generated explanations (including which route terrain slows most). The run is stored in `simulation_runs`. "Apply to all screens" sets the scenario for every screen.

## 16. Limitations (read these)

* **UI pass:** the top-3 actions, the "Why this recommendation?" tiles and the What-If *Recommended Response* are phrased in the frontend from numbers the backend already computed (priority, allocation, routes, simulation); the engines themselves are unchanged and remain in the backend. The Light theme was verified by measuring sampled text/background pairs and by eye in Chromium — not with a full accessibility audit tool, a screen reader or other browsers.

* **Synthetic data only.** Findings are properties of the generator, not of any real supply chain. Forecast accuracy in particular is flattering because the data and the model share assumptions.
* All formulas, thresholds, priority weights and the capacity penalty are documented **assumptions**, not calibrated against real operations.
* The recommendation engine is rules-based; it is not an AI/LLM and does not learn.
* Routes are drawn as simple fictional polylines; "distance" is a seeded number, not computed from road networks. No real elevation or weather data is used.
* IoT is simulated end-to-end; no device authentication, no MQTT, no real RFID/ESP32 firmware.
* No user authentication/authorisation, audit trail, encryption at rest, or hardening — the demo database credentials are `logistics/logistics`.
* Allocation is a greedy, priority-ordered heuristic, not an optimal solver; vehicles serve only their own depot's routes.
* `docker compose up --build` was **not built or run in the development sandbox** (Docker Hub returns 403 there). Container-level behaviour — image builds, Compose DNS, `depends_on`/healthcheck ordering, the `wget`/`pg_isready` health commands — is therefore **untested**; the nginx resolver behaviour was verified against a DNS stand-in on 127.0.0.11, not Docker's own DNS. Please run it once on a machine with internet access.
* The simulation clock is anchored at 2026-06-19 06:00 UTC and runs at 60× for display only.
* The bundle is ~760 kB (no code splitting).
